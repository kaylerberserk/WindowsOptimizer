# Audit « Savage Hunt » — WindowsOptimizer

Machine de référence : **pc-gaming**, Windows 11 **25H2 build 26200.9550** Pro, admin, Secure Boot actif,
x64, GPU NVIDIA. Le script y a déjà été appliqué ~40 fois (39 backups datés du 02 au 21/08/2026).

Tout ce qui suit est **mesuré** sur cette machine ou **documenté** par Microsoft. Rien ne repose
sur de la mémoire. Les points que je n'ai pas pu prouver sont marqués *non vérifié*.

---

## Méthode

Trois instruments, réutilisables, sous `/tmp/opencode/winopt-audit/` :

| Outil | Rôle |
|---|---|
| `check.sh` | Contrat projet complet : ASCII+CRLF (local **et** PowerShell 5.1 réel), structure, résolution `goto`/`call`, `-VerifyOnly` isolé, copie publiée |
| `validate.py` | Modèle cmd.exe : `setlocal`/`endlocal`, `pushd`/`popd`, `goto` en bloc, `if/else`, `set` sans guillemets |
| `symmetry.py` | Audit apply/restore à vue de fichier entier |
| `patch.py` | Édition par octets : refuse d'écrire si le contrat ASCII+CRLF casse, et si un hunk ne matche pas |

Plus des mesures sur la machine (`ssh pc-gaming`) et de la recherche web.

**Résultat du contrôle structurel : le squelette cmd.exe est sain.** 144 labels, 0 orphelin,
profondeur de parenthèses nulle à chaque label, 0 `goto` dans un bloc `()`, tous les `goto`/`call`
résolus, 0 label jamais référencé. Les défauts trouvés sont sémantiques, pas structurels.

## Ce que j'ai corrigé (19 commits, branche `audit/savage-hunt-2026-10`)

### 1. `RunAsPPL` demandait un verrou UEFI quasi irréversible — *corrigé*

Le point le plus grave de l'audit.

Le script écrivait `RunAsPPL=1` dans les **trois** profils, avec le commentaire
« LSA-PPL reste actif sans verrou UEFI : RunAsPPL=1. La valeur 2 pose un verrou UEFI quasi
irreversible ». La cartographie Microsoft est l'inverse :

- `1` = configurer la protection **avec** une variable UEFI
- `2` = configurer la protection **sans** variable UEFI

Une fois la variable dans le firmware, la doc dit que *« the UEFI variable can't be deleted or
changed to configure added LSA protection by modifying the registry or by policy »*. Seule sortie :
`LsaPplConfig.efi` depuis un environnement de récupération. La restauration par
`security-baseline.reg` n'aurait plus fonctionné.

Preuves sur la machine d'audit :
- la baseline capturée par `:CAPTURE_SECURITY_BASELINE` enregistre `RunAsPPL=2 / RunAsPPLBoot=2`
  → c'est le défaut stock, et `2` est bien le défaut d'une installation neuve Win11 22H2+ ;
- l'état après exécution était `1` dans les deux valeurs ;
- WinInit événement 12 à **chaque** démarrage : *« LSASS.exe a démarré en tant que processus
  protégé avec le niveau 4 »* → la protection est bien active, c'est le mode qu'il ne faut pas
  verrouiller qui était demandé.

Le script demandait le mode le plus dur à rétracter en écrivant qu'il évitait ce mode. Corrigé
en `/d 2` aux trois endroits, y compris la base « stock » de la restauration.

*Non vérifié :* la lecture des variables UEFI est bloquée pour un appelant en mode utilisateur sur
25H2 (erreur 87 même pour `BootOrder`), donc je ne peux pas confirmer si le firmware a reçu la
variable. Le registre est revenue à 2 ; un firmware déjà écrit exigerait l'outil Microsoft.

### 2. La désinstallation OneDrive pouvait détruire Bureau / Documents / Images — *corrigé*

OneDrive Known Folder Backup déplace ces trois dossiers **dans** `%USERPROFILE%\OneDrive` dès la
connexion à un compte Microsoft, ce qui est le défaut de Windows 11. L'étape 6 supprimait ce
dossier inconditionnellement : sur un tel profil, les fichiers non hydrates (« Fichiers à la
demande ») n'existent plus que sur le cloud, inaccessible sans le client.

La suppression n'a plus lieu que si aucune valeur `User Shell Folders` ne pointe dans OneDrive.
Détection volontairement large : un faux positif ne fait que conserver le dossier, un faux négatif
perd des fichiers.

Logique vérifiée sur 25H2 : présent → 1, absent → 0, insensible à la casse, profil réel → 0
(donc suppression normale). Les formes d'expansion immédiate et retardée ont été contrôlées
après le `set`, et le `>` des messages reste échappé en `^>`.

Sur pc-gaming le risque ne se matérialise pas (KFM inactif, dossiers locaux) — mais c'est le cas
de la majorité des postes ayant un compte Microsoft.

Au passage : les trois `timeout /t` qui attendaient que OneDrive libère ses fichiers sont
remplacés par `ping -n`, car `timeout` **échoue silencieusement dès que l'entrée standard est
redirigée** — ce qui annulait exactement l'attente utile.

### 3. Le DoH n'était jamais activé — *corrigé*

`DnsOverHttpsMode` valait `allow`. Microsoft ne documente que trois valeurs : `off`, `automatic`,
`secure`. `allow` n'en est pas une → **la politique entière était ignorée**, `DnsOverHttpsTemplates`
compris. Le script annonçait « Navigateurs optimisés » alors que le DoH n'était jamais activé et
le résolveur Cloudflare jamais utilisé.

`automatic` est littéralement ce que décrivait déjà le commentaire du script. `secure` reste écarté
(casse les réseaux filtrés/proxy).

### 4. Sept défauts structurels — *corrigés*

| Correctif | Mesure |
|---|---|
| ESC : astuce CMD `prompt $E` avant le spawn PowerShell | **16 ms vs 164 ms**, PROMPT parent intact |
| Backups : purge à 5 copies | **39 copies / 12,9 Mo** constatés, une par exécution, sans limite |
| `powercfg` : retire une sonde `findstr` qui ne peut jamais réussir | le plan `e9a42b02` est masqué de `powercfg -list` |
| Réseau : retire `loopbacklargemtu` écrit ici **puis** réécrit 60 lignes plus loin | une des deux paires s'exécutait toujours |
| Réseau : `forcews` hors de la branche de profil | `default` et `enabled` donnent le même état (`netsh ... heuristics help`) |
| Réseau : l'échec MSI pose `NETWORK_SECTION_ERROR` | seul échec de la section invisible dans `exit /b` |
| `END_SCRIPT` : `ping -n 4` au lieu de `timeout /t 3` | même raison que OneDrive |

## Décisions d'axe que je te laisse trancher

Je n'ai **pas** touché à ces valeurs : elles engagent ton choix d'usage, pas un bug.

**`NetworkPredictionOptions=0`** — 0 = « prédire sur toute connexion », ce qui impose prerefetch
DNS, préconnexion TCP/SSL et prerendering. Pour une latence gaming c'est défendable ; pour
« moins d'activité réseau de fond » c'est l'inverse. À toi de dire.

**`pacingprofile=always`** — le mécanisme est différent de celui du commentaire : BBR2 pace en
interne, le knob `netsh` est un pacer de pile expérimental, off par défaut. Enaxo Layered ->
double-pacing. Source à trancher.

**`LongPathsEnabled` sur l'axe usage** — Gaming=1 est sans effet (opt-in applicatif via manifeste),
Normal=0 casse git, Python, `node_modules` et les installeurs à 260 caractères. Le côté Normal
est celui qui pose problème.

**`EnableLUA=0`** pour « moins de confirmations » — Microsoft recommande de ne pas l'utiliser et
la désactivation casse l'Admin Approval Mode. `ConsentPromptBehaviorAdmin=0` atteint l'objectif.

## Réfutations — ce que j'ai vérifié et qui est *faux*

Autant de valeur dans un constat annulé que dans un constat posé.

- **`start /wait` ne propagerait pas le code de sortie.** Faux. Mesuré sur 25H2 : 7, 1638 et 3010
  remontent correctement. Un chasseur recommandait de supprimer `start /wait` de l'installateur
  VC++ et de traiter les codes 3010/1641/1638 comme du code mort. C'est faux — je n'ai rien touché.
- **`powercfg /setactive e9a42b02` permettrait d'éviter le doublon.** Faux, testé : renvoie 1
  (« écriture sur un paramètre non pris en charge »). Le plan est enregistré mais non activable ;
  la duplication est le seul chemin fonctionnel. J'avais d'abord conclu à un bug, le test m'a
  corrigé. Le script n'est pas à blâmer là-dessus.
- **`= 0` sur `NtfsDisableLastAccessUpdate` serait la valeur d'origine.** Refuté par la mesure :
  `0x80000002` (-2147483646) sur le stock. Le doute légitime porte sur le *delete* de la branche
  Gaming, pas sur la valeur cible.
- **Le fichier serait structurellement fragile.** Non : 144 labels, 0 orphelin, profondeur nulle,
  0 `goto` en bloc. Le problème est sémantique.

Un piège d'outillage a aussi été désamorcé : mon parseur traitait `;` comme un commentaire.
`cmd.exe` ne le fait pas. Le script ne tombe pas dedans — mais l'outil, si.

## Constats relus et non corrigés

Relecture intégrale des rapports tardifs (second-pass, menus, publication, performance,
économies d'énergie). **Rien ici n'a été modifié** : ce sont soit des décisions d'axe qui
te reviennent, soit des nettoyages à faire à ton rythme. Pour chaque ligne, je précise si
**moi-même** je l'ai recontrôlée sur la machine — c'est le cas de toutes celles marquées
« revérifié ».

### Inversion de polarité — `ReadyBoot` activé dans un bloc « autologgers OFF`

`L1229` écrit `WMI\Autologger\ReadyBoot\Start = 1`, c'est-à-dire **activé**, juste après
avoir mis `AppModel`, `Cellcore`, `SQMLogger` et `Diagtrack-Listener` à `0` et `DiagLog` à `0`
hors portable Normal+Eco. Le commentaire du bloc annonce « Autologgers de diagnostic OFF »
et le script termine par « Taches de telemetrie desactivees ». Les quatre autres sont
cohérents, celui-là est inversé.

À noter : sur pc-gaming la valeur relevée est `0`, pas `1`. Donc soit l'écriture est refusée
en silence, soit elle n'a pas eu lieu lors du dernier passage. Dans les deux cas le
`[FAIT]` final n'a rien à vérifier.

**Revérifié :** `ReadyBoot\Start = 0x0` sur la machine ; le code écrit bien `1`.

### `DisableAntiSpyware` : politique retirée par Microsoft, écriture sans effet

`L3240` écrit `Policies\...\Windows Defender\DisableAntiSpyware=1`. Microsoft a supprimé
cette politique (Windows 10 2004) ; seul `DisableAntiVirus` existe encore.

**Revérifié :** après une quarantaine d'exécutions, `DisableAntiSpyware` est **absent** du
registre alors que `DisableAntiVirus=1` est présent, sur la même clé. L'écriture ne prend
pas — et le `reg add` avalé son erreur.

### `LongPathsEnabled` : la branche « Normal » retire une capacité du stock

`L1607` (Gaming) écrit `1`, `L1610` (Normal) écrit `0` en annonçant « Chemins longs rendus au
stock Windows ». Le stock mesuré vaut `1`. La branche Normal supprime donc une capacité
documentée (chemins longs) tout en prétendant restaurer le stock.

C'est une décision d'axe : Gaming=1 ne gêne pas les jeux (opt-in applicatif), mais Normal=0
casse git, Python, `node_modules` et les installeurs à 260 caractères. **Je n'ai pas touché.**

**Revérifié :** `LongPathsEnabled = 0x1` sur la machine.

### `DisableAntiSpyware`, `store.db`, Cortana, `Typelib` — du folklore coûteux

Relevés et mesurés, mais sans effet ou nuisibles ; le détail par détail est dans le rapport
relu. Le plus net : le bloc `store.db` (16 lignes + commentaire) garde un fichier que Windows 11
ne livre plus, et le hack `Typelib {8cec5860-...}` **crée** deux clés qui n'existent pas
pour casser une typelib COM — c'est-à-dire à l'inverse de ce qu'il prétend.

### Ce que le chasseur a écrit et qui est faux, sur ces mêmes sections

Pour éviter qu'on « corrige » des choses qui marchent, la relecture confirme comme **correct**
malgré des avis contraires : `MitigationOptions` et `DisableExceptionChainValidation` sous
`Session Manager\Kernel` (et non `Memory Management`) ; `WdBoot`/`WdFilter` à `start=boot` ;
`NtfsDisableLastAccessUpdate=0x80000002` = « laisser Windows gérer » ; le GUID `SCHEDPOLICY`
est bien l'Intel Thread Director ; le bloc `hosts` de télémétrie est idempotent ; les
deux `choice.exe` du launcher répondent 200 ; le mécanisme de `SFIO` sous `Games` est correct.
